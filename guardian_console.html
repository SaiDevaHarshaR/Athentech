Diagnostics, without guesswork.

Choose a client and perform one focused check at a time. Checks read data; they do not edit LIS tables.

Select a client

Use the activation code associated with the institution.

What is schema diagnostics?

Shows which tables and columns Guardian has detected, the effective collection metric, available report capabilities, and rejected client configuration pins. Use it when a report is wrong or unavailable.

What is schema snapshot comparison?

Compares today's detected database columns with the previous recorded snapshot to highlight newly added or missing fields. It may update Guardian's local snapshot metadata, but not the client's LIS tables.

Why refresh cached profile?

Sahasra keeps detected mappings in memory for up to six hours. Refresh only the selected client's profile after a verified schema/config change. It does not rewrite client records.

Diagnostic results

What happens when you refresh a profile?

Only the selected client's cached schema mapping is refreshed. The underlying client SQL Server tables are not changed. If a check reports a missing field, open Playbooks before making any configuration changes.

Practical recovery

▦ Excel collection export+
  1. Verify whether the problem affects Today, Yesterday, or This Month.
  2. Open Diagnostics and run a client self-check.
  3. Review the collection metric and rejected mappings in schema diagnostics.
  4. Compare the exported figures with verified SQL Server values. Billed totals must not be presented as cash collected.
  5. If monthly only fails, send the support report to your technical contact.
Do not manually edit collection tables or overwrite another client's metric configuration.
⌁ SQL Server connection failed+
  1. Check whether other clients are responding normally.
  2. Run the affected client's self-check once the circuit breaker allows a retry.
  3. Ask the database administrator to verify server reachability and login permissions.
  4. Check for a recent host, firewall, password, or network change.
  5. Retry the same read-only report after connectivity is restored.
Never change client database credentials or permissions without authorization.
◇ AI Agent response failed+
  1. Try a known instant report to separate SQL/database errors from AI-provider errors.
  2. Check Guardian signals for rate limits, timeouts, or schema errors.
  3. Confirm the LLM provider credentials and quota in the secure server settings.
  4. If only one client is affected, run its self-check.
  5. Escalate with the sanitized report if errors persist.
□ PDF / Smart Report failed+
  1. Check whether a normal text report works for the same patient or UHID.
  2. Confirm the patient identity and required authenticated results exist.
  3. Check backend errors for template, renderer, or AI provider failures.
  4. Confirm sufficient storage and browser-renderer availability on the app server.
  5. Do not substitute another patient's data when a report cannot be generated.
◈ Admin panel or sign-in issue+
  1. Check whether the Guardian console page loads.
  2. If login reports HTML instead of JSON, check the IIS rewrite rule for /admin/guardian/*.
  3. Test the corresponding local FastAPI endpoint on the actual backend port.
  4. Check admin-account status and authentication logs.
  5. Avoid deleting or reseeding admin tables as a troubleshooting shortcut.
↗ Client schema changed+
  1. Run Diagnostics → Compare schema snapshot.
  2. View current schema diagnostics for missing columns and rejected pins.
  3. Refresh only the client's schema cache and recheck.
  4. Confirm any new column mapping with the LIS vendor or technical owner.
  5. Escalate if the table family itself has changed.
Schema refresh is not a database migration. It does not create or alter client tables.
◇IIS 404 — Guardian route+
  1. Verify the FastAPI route responds from localhost on the server.
  2. Open IIS URL Rewrite for the Sahasra site. Confirm /admin/guardian/* forwards to the FastAPI port.
  3. Keep the specific Guardian rewrite above static-file rules and stop subsequent processing.
  4. Retest the public HTTPS route.
Do not change client database settings to fix an IIS routing problem.
◇Unexpected token < — HTML returned instead of JSON+
  1. Check the failed browser request in Network → Response; an HTML page means the API route was not reached.
  2. Verify /admin/guardian/api/* is forwarded to FastAPI by IIS.
  3. Test the local FastAPI login endpoint and compare the public URL.
  4. Ensure the rewrite preserves the request method and query string.
Never paste admin passwords into logs or support tickets.
◈Guardian sign-in rejected+
  1. Confirm you are using Guardian’s admin credentials, not a LIS activation code.
  2. Review whether the admin account is enabled and whether credentials have expired.
  3. Check backend authentication events and request status codes.
  4. Have an authorized administrator reset credentials using the established admin procedure.
Do not modify or delete admin tables to reset a password.
◇401 / 403 permission denied+
  1. Sign out and sign back in to obtain a fresh session token.
  2. Confirm the action uses an account with the correct administrative role.
  3. If only one client fails, verify its assigned permissions and activation scope.
  4. Escalate persistent 403s with a redacted support report.
Do not bypass access checks or share tokens.
◇SQL Server timeout or communication link failure+
  1. Check whether the failure affects one client or all clients.
  2. Run a client self-check if the database is reachable.
  3. Ask the database administrator to check connection limits, VPN/firewall reachability, and server load.
  4. For a long export, retry a smaller period only once, then escalate.
Avoid repeated retries that overload SQL Server.
◈Missing SQL table or column+
  1. Inspect client schema diagnostics and rejected mappings.
  2. Compare with the last known schema snapshot.
  3. Refresh only that client’s schema profile if the database schema has changed.
  4. Ask the LIS vendor to confirm the new column/table meaning before setting a pin.
Never create or alter LIS tables to make a report run.
◇Incorrect collection totals+
  1. Identify whether the report represents billed revenue or actual received payments.
  2. Review the client’s collection metric pin and Amount Source fields.
  3. Compare sample bills and totals independently with authorized SQL reporting.
  4. Escalate if credits, refunds, concessions, or payment modes are being combined incorrectly.
A TOTALAMOUNT fallback does not prove payment receipt.
◇Collection Excel displays zeros+
  1. Run a short daily export first and inspect both amount columns.
  2. Check the client’s schema profile and effective collection metric.
  3. Confirm the selected amount is based on the intended source and not a missing-column default.
  4. Compare results with the LIS source records before approving the workbook.
Do not relabel billed amounts as cash collected.
◈Monthly Excel fails but daily works+
  1. Verify the Today and Yesterday exports succeed for the same client.
  2. Check whether the month includes many branches or thousands of records.
  3. Review backend export logs and database execution time.
  4. Escalate for batching or streaming optimization if the whole month keeps failing.
Do not repeatedly run the full monthly report during a database outage.
◇Excel wrong branch or payment mode+
  1. Inspect transaction rows for original LOCATIONID and MODE values.
  2. Compare the rendered branch/payment labels against database master tables.
  3. Confirm whether the report query supplies the actual mode or a default.
  4. Escalate with sample anonymized rows showing the mismatch.
Never assume every missing payment mode is Cash.
◇Recent patients missing or outdated+
  1. Ask Recent Patients for the affected institution, then compare with the patient registration screen.
  2. Check the patient-date field in schema diagnostics and the most recent REGDATE in SQL.
  3. Verify the activation code points to the intended database, including test vs production.
  4. Escalate if the underlying data is correct but results are stale.
Do not edit patient registration records to fix display issues.
◈Smart Report shows wrong or missing patient+
  1. Verify the report was requested using the correct UHID and institution.
  2. Cross-check bill and investigation identifiers before relying on the output.
  3. Confirm only authenticated investigation results are included where required.
  4. Stop distribution and escalate any possible patient mixing immediately.
Never use or distribute a report whose patient identity is uncertain.
◇PDF renderer unavailable+
  1. Try a simple text report to isolate the problem to PDF generation.
  2. Check backend logs for Chromium/Playwright or template exceptions.
  3. Verify the approved renderer installation and server storage are intact.
  4. Escalate if the process crashes or times out repeatedly.
Do not disable patient identity checks to make PDF export succeed.
◇AI gives a wrong intent or fabricated answer+
  1. Repeat once with a clear question specifying client, date range and report.
  2. Compare numeric answers with a verified LIS report or authorized SQL result.
  3. Record the input and sanitized output for support.
  4. If accuracy remains uncertain, stop relying on the AI result and escalate.
Do not treat fluent AI text as verified financial or clinical data.
◈AI provider rate limit or outage+
  1. Identify whether instant database reports still work.
  2. Check the AI provider’s service status, available quota and configured model.
  3. Wait for the provider rate limit to clear rather than repeatedly retrying.
  4. Escalate if the provider credentials or subscription have changed.
Do not expose API keys in screenshots or support reports.
◇Circuit breaker paused a client+
  1. Check the client name and failure category in Guardian status.
  2. Allow the cooldown period to expire before retrying.
  3. Run a self-check once; verify the underlying connection is stable.
  4. Escalate repeated trips; other client databases should stay available.
Never disable circuit breakers as the first troubleshooting step.
◇Activation code invalid or expired+
  1. Confirm the entered code is assigned to the intended institution.
  2. Check activation validity and expiry using authorized admin tools.
  3. Check for network or clock issues affecting verification.
  4. Contact the licensing administrator for renewal or correction.
Do not issue replacement activation codes from Guardian.
◈Config pin ignored or rejected+
  1. Check that the file is under config/clients with the exact database name.
  2. Open schema diagnostics to see whether the pin applied or was rejected.
  3. Check JSON formatting and whether pinned column names exist in that database.
  4. Refresh only this client’s cached profile and verify the effective metric.
Do not copy another client’s pin without verifying financial semantics.
◇One client has no pharmacy or inventory+
  1. Check whether the institution has a pharmacy module at all.
  2. Inspect capabilities and confirm expected pharmacy tables exist.
  3. If tables are absent, explain that the report is unsupported.
  4. Escalate for a supported pharmacy schema mapping rather than defaulting stock to zero.
Unavailable stock data must not be reported as zero inventory.
◇Service unavailable / 502 / 503+
  1. Check whether the FastAPI health endpoint is accessible locally.
  2. Confirm the SahasraAIAgent Windows service is running.
  3. Inspect recent application startup errors and the IIS reverse proxy target.
  4. Escalate before restarting repeatedly if startup keeps failing.
Do not modify client SQL permissions to fix service routing.
◈Dashboard or Guardian data looks stale+
  1. Refresh the overview and note its timestamp/source where available.
  2. Check whether a specific client’s schema profile needs refreshing.
  3. Verify you are opening the expected environment and not a cached browser tab.
  4. If backend values remain stale, gather a support report.
Refresh is a read-side cache action, not a database repair.
◇Deployment caused a regression+
  1. Record the first failure time and the last known working release.
  2. Run the standard smoke tests for at least three different LIS clients.
  3. If critical functions broke, use the approved tested rollback procedure.
  4. Escalate with release version, logs, and affected routes.
Do not overwrite a working production release without a backup.
◇Data privacy or cross-client mix-up+
  1. Stop the affected output and restrict access immediately.
  2. Capture sanitized incident details: time, request type and client identifier.
  3. Notify the organization’s security or technical escalation contact.
  4. Do not retry with real patient data until tenant isolation is verified.
Treat any cross-client patient exposure as a security incident.
◈Slow performance under heavy load+
  1. Check whether the issue is limited to a client or affects the whole service.
  2. Identify the slow API action and reporting date range from logs.
  3. Avoid parallel bulk exports while investigating database load.
  4. Escalate for connection-pool, pagination, or query-plan review.
Avoid broad SQL changes without testing on a nonproduction system.

1. What is Sahasra Guardian?

Guardian is a support workspace for the Sahasra AI Agent. It reports recent client-specific errors, offers plain-language troubleshooting, and checks whether a client database is reachable and its expected schema can be read. It does not replace the main Admin panel; the two serve different purposes.

2. First-time use

  1. Open the Guardian Console link on your deployed Sahasra website.
  2. Sign in using the same authorized admin account.
  3. The Overview page opens automatically; the sign-in form disappears.
  4. Review incidents. A temporarily paused client usually means repeated database failures triggered its circuit breaker.
  5. To investigate a client, choose Diagnostics at the top and enter its activation code.
  6. Start with Run self-check, then use the other tools only as needed.
  7. Use Playbooks for recovery steps, or export the support report if escalation is necessary.

3. What each button does

ButtonWhat happens
Refresh statusRequests the current Guardian status and recent incidents from the backend.
Run self-checkChecks one client's connection, available schema information, and configured mappings. It is intended to be read-only.
View schema diagnosticsDisplays what Guardian detected about the client's report capabilities and configuration.
Compare schema snapshotCompares the current client schema with the previously saved snapshot. Its snapshot metadata may be updated, but LIS tables are not supposed to be modified.
Refresh cached profileRebuilds the selected client's cached schema profile without editing its LIS data.
Download support reportDownloads a sanitized JSON diagnostic report to share with technical support.
Sign outClears the Guardian session token held in this browser page.

4. What to do when something fails

  1. Note the client, time, and action that failed.
  2. Open Diagnostics and perform a client self-check.
  3. Open Playbooks and follow the matching guide.
  4. If the error remains, click Download support report.
  5. Share it securely with your designated technical contact. Never send passwords or full patient data.

If the Guardian login itself fails, check whether IIS is rewriting /admin/guardian/* requests to FastAPI rather than serving a static 404 or HTML error page.

5. Limits and safety

  • Guardian can explain errors and run the supported checks. It cannot guarantee repair of a new code bug.
  • Do not treat automatic collection-column detection as proof of accounting meaning; distinguish billed amounts from received money.
  • Do not grant write access to client LIS databases just to make a report work.
  • Keep backups, known-good app releases, and a named technical escalation contact.
  • Not all incidents are detected immediately; status reflects what the deployed backend has recorded.
